# 08 · 反降智红线与判定案例

省 token 最容易走偏的地方：**把「省」做成了「糊弄」。** 这一章是护栏。

## 1. 判定树

```
这段内容要不要省？
│
├─ 删掉它，我会不会可能答错？
│   ├─ 会 → 不许省（载荷）
│   └─ 不会 → 继续
│
├─ 它会不会在后续轮次重复出现？
│   ├─ 会 → 落文件 + 留指针（省最多）
│   └─ 不会 → 正常写
│
└─ 它是过程还是结论？
    ├─ 过程 → 压成 1 行或丢给子代理
    └─ 结论 → 留
```

## 2. 十二红线（附判定案例）

### 1. 首次完整报错
❌ `grep -m1 error` 就下结论
✅ 第一次要看完整堆栈 + 错误码 + 触发命令；后续才用 `grep`

### 2. 测试与构建
❌ 「改动很小，应该没问题」
✅ 跑一遍，贴退出码

### 3. 用户约束原文
❌ 把「必须兼容 PHP 7.4」记成「尽量兼容」
✅ 原样记进 HANDOVER

### 4. 数字
❌ 「端口大概是 8080」
✅ 从配置里读出来再写

### 5. 接口契约
❌ 「返回一个 user 对象」
✅ `{id: number, name: string, role: 'admin'|'user'}`

### 6. 安全代码
❌ 凭印象写鉴权
✅ 读现有实现 + 对照框架文档

### 7. 并发与边界
❌ 只测 happy path
✅ 空值、超时、重试、并发写

### 8. diff 复查
❌ 改完直接提交
✅ `git diff` 看完整改动

### 9. 依赖版本
❌ 「装最新版」
✅ 锁版本，写进 lockfile

### 10. 破坏性操作影响面
❌ 直接 `rm -rf`
✅ 先 `ls` / `du -sh` / 确认路径 + 备份

### 11. 不确定时查证
❌ 猜 API 参数
✅ 读文档或 `--help`；一次查证 ≈ 几百 token，猜错 ≈ 几千

### 12. 推理
❌ 「省 token 就少想点」
✅ 思考是投资。要砍的是 I/O 和搬运，不是推理深度

## 3. 「省过头」的五个信号

1. 开始用「应该」「大概」「通常」描述可验证的事实
2. 没跑测试就说完成
3. 报错只看第一行
4. 改代码没看上下文
5. 子代理结论没抽检就用

出现任一 → 停下来补验证。

## 4. 「假省」的四种形态

| 形态 | 表面 | 实际 |
|---|---|---|
| 砍验证 | 快 | 返工三次 |
| 砍上下文 | 省 | 改错行，重写 |
| 砍澄清 | 省一轮 | 做错方向，全废 |
| 砍交接 | 省 300 token | 下个会话重摸 2 小时 |

## 5. 质量守恒等式

```
省下的 token  ≤  省下的搬运 + 省下的重复 + 省下的探索
省下的 token  ≠  省下的核实 + 省下的推理 + 省下的验证
```

违反这个等式，就是拿质量换钱，长期一定亏。

## 6. 交付前五问

1. 结论有证据吗？（文件:行号 / 命令输出）
2. 跑过验证吗？（测试 / 复现 / 手动点一遍）
3. 用户约束都满足吗？
4. 有没有把不确定写成确定？
5. 下个会话只看 HANDOVER 能接手吗？

五问全过才算完。
