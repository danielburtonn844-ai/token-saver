# 07 · 输出格式压缩

回复也是 token，而且会进入历史，**在后续每一轮重复计费**。所以啰嗦的回复是复利负债。

## 1. 三段式默认结构

```
结论：一句话说清结果
证据：≤ 8 行（表格 / 关键片段 / 命令输出）
下一步：1~3 条可执行动作
```

不要开场白、不要「好的」、不要复述需求、不要「希望对你有帮助」。

## 2. 各类内容的压缩写法

### 2.1 代码

❌ 整文件重贴 300 行
✅ 只贴 diff 或改动片段

```diff
- if (user.role = 'admin')
+ if (user.role === 'admin')
```

### 2.2 表格

只给差异行 + 关键行。全量表放文件，给路径。

### 2.3 日志

头 5 行 + 错误行 + `[共 12,345 行，全文 /tmp/x.log]`

### 2.4 步骤

```
1. 动作 —— 命令
2. 动作 —— 命令
```

不要每步配一段解释。解释只在「为什么」不显然时给一句。

## 3. 什么必须完整写出来

- 破坏性命令（`rm -rf`、`DROP TABLE`、`git reset --hard`）——必须写全，不许缩写
- 路径、URL、ID、版本号
- 报错原文
- 用户的硬约束

## 4. 长度参考

| 场景 | 目标长度 |
|---|---|
| 简单查询 | ≤ 5 行 |
| 单步操作完成 | ≤ 15 行 |
| 多步任务交付 | ≤ 40 行 + 文件路径 |
| 需要用户决策 | ≤ 10 行（问题要具体） |

超过就说明该落文件了。

## 5. 结构化优先

能用表格就不用段落；能用列表就不用散文。
但**不要为了排版而排版**——三行能说清的，别做成 10 行表格。

## 6. 重复的处理

| 情况 | 写法 |
|---|---|
| 前面说过的 | 「见上」/ 给章节号 |
| 用户刚说过的 | 不复述，直接回答 |
| 自己上一轮说错的 | 一句话更正，不重述原文 |

## 7. 反模式

| 反模式 | 代价 |
|---|---|
| 「让我来分析一下…」 | 纯废话，还进历史 |
| 每轮末尾总结一次 | 30 轮 = 30 份摘要 |
| 把用户问题复述一遍再答 | 双倍 |
| 大量 emoji / 分隔线 | 纯装饰 token |
| 同一结论在三个小节重复 | 三倍 |
