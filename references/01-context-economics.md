# 01 · 上下文经济学

## 1. 单轮成本的真实结构

一次请求的输入 token 不是「你刚打的字」，而是：

```
输入 = 系统提示 + 工具定义 + 技能文本 + 全部历史消息 + 本轮新内容 + 附件/图片
```

历史是**每一轮都重发一遍**的。所以第 `i` 轮的输入 `C_i` 包含第 1 到 i−1 轮的全部内容。

## 2. 累计成本公式

设会话共 `N` 轮，初始上下文 `C₀`，每轮平均净增 `Δ`（扣掉被截断的部分）：

```
ΣC = N·C₀ + Δ·N(N−1)/2
```

- 第一项：固定开销 × 轮数（线性）
- 第二项：增量累积（**二次**）

### 算例（C₀ = 20K, Δ = 3K, N = 30）

| 方案 | 累计输入 | 相对基线 |
|---|---|---|
| 基线 | 1,905,000 | — |
| Δ 压到 1K | 1,035,000 | −46% |
| N 压到 15 | 405,000 | −79% |
| 两者都做 | 195,000 | **−90%** |

**推论：把「30 轮」变成「15 轮」比把每条命令砍一半更值钱。** 所以优先合并操作、批量执行、减少澄清往返。

## 3. 三个杠杆的正确使用顺序

### 3.1 先砍轮数（平方项）

- 一次 shell 调用里跑完 5 条独立命令，而不是分 5 轮
- 相关文件用一次 `grep -n` + 一次 `file_read` 窗口读完，而不是逐个试
- 澄清问题一次问完（最多 4 条），不要挤牙膏
- 能并行发起的工具调用放在同一个 block

### 3.2 再砍每轮增量（线性项）

- 工具输出裁剪：头 30 + 尾 20 + 命中行
- 不把完整文件读进来，只读改动窗口
- 回复不重复用户原话、不重贴旧内容
- 图片/截图只在必要时用

### 3.3 最后砍初始上下文

- 技能按需加载（progressive disclosure）
- 项目给一张「索引卡」，不读全库
- 常驻内核 ≤ 200 token

## 4. token 估算方法（不接 tokenizer 也能估）

| 内容 | 粗估 |
|---|---|
| 中文（含全角标点） | 1 字 ≈ 1.24 token |
| 英文字母与空格 | 1 字符 ≈ 0.19 token（约 5 字符/token） |
| 数字与符号 | 1 字符 ≈ 0.64 token |
| 代码 | 1 字符 ≈ 0.3 token |
| JSON / 日志 | 1 字符 ≈ 0.28 token |
| 图片 | 一张普通截图 ≈ 1000~1600 token |
| 表格 | 按字符数估，但渲染后更贵 |

脚本共用 `token_saver/text.py` 这一份估算：对 cl100k_base 实测校准，
中位误差 4.9%、p90 7.2%、最大 11.3%（50 份样本，训练/测试各半，见 `bench/CALIBRATION.md`）。
可用于取舍判断，不要用来核对账单。

## 5. 预算分配建议

一次任务的总输入预算（按 1M 上限的模型算）：

| 阶段 | 占比 | 说明 |
|---|---|---|
| 常驻（系统+技能+工具定义） | ≤ 10% | 越少越好 |
| 探索（读文件/跑命令） | 30~40% | 主力开销，靠外派压 |
| 推理与实现 | 30% | 不许压 |
| 收尾与验证 | 15~20% | 不许压 |
| 缓冲（重试/返工） | 10% | 压到 0 就会爆 |

## 6. 子代理的盈亏平衡

外派成本 = `B`（写 brief）+ `S'`（子代理自己烧的，不回主上下文）+ `R`（结论回流）。
自己做成本 = `S`（脏输出全进主上下文）+ 后续每轮都被它拖着走。

因为主上下文里的脏输出会在**剩下每一轮**重复计费，实际代价是 `S × 剩余轮数`。

```
外派划算 ⟺ S × R_remain > B + R
```

经验阈值：`S > 20KB` 或 `轮次 > 6`，直接外派。
若只剩 1~2 轮就结束，别外派——省不下。

## 7. 缓存经济学

命中缓存的输入通常按 10% 计价（各厂商不同）。这意味着：

- 同一段 20K 的技能文本，读一次 vs 读十次，成本差 10 倍
- **稳定前缀** = 系统提示 + 技能 + 项目约定，放最前面，一次成型
- **变动内容** = 本轮问题、新日志，放最后
- 中途编辑前缀 → 缓存全废 → 等于重新付一次全量

实践：把「项目约定」写成独立文件，会话开头读一次，之后不再改。

## 8. 什么时候「不省」反而是省钱

| 场景 | 省了会怎样 |
|---|---|
| 跳过测试 | 上线炸 → 回滚 + 重做，成本 10 倍 |
| 只看摘要改代码 | 改错行 → 二次返工 |
| 不读完整报错 | 猜错根因 → 试 5 个方案 |
| 不问清需求 | 做错方向 → 全废 |
| 不写交接 | 下个会话重新摸一遍 |

**判断标准：这次省下的 token，是否可能换来一次返工？** 会 → 不省。
